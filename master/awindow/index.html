    AWindow#

    Represents a window in the underlying windowing system.

    Header:#include <AUI/Platform/AWindow.h>
    CMake:aui_link(my_target PUBLIC aui::views)

    Detailed Description#

    Opening a window#

    Create an AWindow, put views into it with AWindow::setContents and call AWindow::show:

    #include <AUI/Platform/Entry.h>
#include <AUI/Platform/AWindow.h>
#include <AUI/View/ALabel.h>

AUI_ENTRY {
    auto window = _new<AWindow>("Hello AUI", 300_dp, 200_dp);
    window->setContents(Centered { Label { "Hello, world!" } });
    window->show();
    return 0;
}

    Every window implicitly holds the application (see AApplication::Hold), so by default the application keeps running while at least one window is alive. This is adjustable: create an explicit hold with AApplication::hold() to keep the application running after the last window is closed, or release it to allow the application to exit. The window is owned by AUI while it is shown, so you don't have to store the pointer; store it only if you want to talk to the window later.

    To open another window from the application (i.e., a settings dialog), do the same from any slot or callback on the UI thread:

    connect(settingsButton->clicked, this, [this] {
    auto settings = _new<AWindow>("Settings", 400_dp, 300_dp);
    settings->setContents(Vertical { Label { "Settings go here" } });
    settings->show();
});

    AWindow(title, width, height) creates an ordinary window with the OS-drawn titlebar. Anything else (a parent window, modality, custom titlebar, fixed size) is configured with AWindow::Init, see below. To close the window from code, use AWindow::close.

    Architecture#

    This document covers AUI's window management system, which provides cross‑platform window creation, lifecycle management, and event handling. The system abstracts native windowing APIs across Windows, Linux, macOS, Android, and iOS platforms while maintaining a unified interface for application developers.

    AWindow is the concrete implementation of a UI surface that is backed by a native window. It inherits from ASurface – the generic surface API that can be used by other windowing API implementations (i.e., SDL3 or a game engine).

    AWindow owns an IRenderingContext instance. The context bridges the window to the shared IRenderer – the actual rendering engine. The renderer performs all drawing primitives and is shared across all windows. The context handles platform‑specific tasks such as buffer swapping, resizing, and screenshot capture.

    Creation, decorations and modality#

    AWindow is created with AWindow::Init - an aggregate describing everything that can't be changed afterwards:

    _new<AWindow>(AWindow::Init {
    .title = "Settings",
    .width = 400_dp,
    .height = 300_dp,
    .parent = AWindow::Init::Parent { .window = *this, .modal = true },
    .decoration = AWindow::Init::DecorationDefault { .buttons = { .minimize = false, .maximize = false } },
    .resizable = false,
});

    Meaningless combinations do not compile: modality exists only as a part of parent, window buttons exist only in decorations which have them.

    Decoration What it is Replaces
    DecorationDefault { buttons } Ordinary OS-drawn titlebar and border. WindowStyle::DEFAULT, NO_MINIMIZE_MAXIMIZE
    DecorationExtended { buttons } Window contents extend into the titlebar. Native window controls are kept where the platform has them. ACustomCaptionWindow
    DecorationBorderless { shadow } No titlebar, no buttons. Native border, shadow and rounded corners are kept where possible. ACustomWindow, NO_DECORATORS

    A modal window blocks user input of its parent until closed. Having parent without modal produces an ordinary child window - it does not block anything, even when it is not resizable.

    Titlebar of Extended and Borderless windows#

    declarative::Titlebar is a view you place into the window contents yourself; it is not created by the window. It is both a drag handle and a layout container for the titlebar contents. What it does depends on the decoration:

    DecorationExtended DecorationBorderless
    Drags the window yes yes
    Double click maximizes/restores yes yes
    Window controls (close, minimize, maximize) yes: native or drawn by AUI, according to buttons no, declarative::Titlebar is just your contents
    Space reserved for native controls yes (AWindow::windowControlsInsets) no, zero

    Without declarative::Titlebar a Borderless window can't be moved by the user at all, and an Extended window has no draggable area.

    What can be put into declarative::Titlebar of a Borderless window: any view. Contents are laid out horizontally, the first and only child stretches over the full width. Put a label for a plain caption, or a Horizontal with a logo, title, search field, tool buttons and so on:

    auto w = _new<AWindow>(AWindow::Init {
    .title = "Custom window without caption",
    .width = 400_dp,
    .height = 300_dp,
    .decoration = AWindow::Init::DecorationBorderless {},
});
w->setContents(Vertical {
    // an opaque caption strip: the window is dragged by it
    Titlebar { Label { "Drag me" } AUI_OVERRIDE_STYLE { Padding { 4_dp } } },
    Centered { Label { "Window contents" } } AUI_LET { it->setExpanding(); },
});
w->show();

    Nothing is drawn by the window itself, so everything about the look (background, height, padding, border) is up to you and set by ASS on declarative::Titlebar or its contents. Interactive views inside the titlebar work as usual: buttons (AButton) and views with .override-title-dragging ASS class are not drag areas, everything else under declarative::Titlebar (labels, spacers, empty space, text fields included) starts window dragging.

    With DecorationExtended the window contents extend under the system titlebar, so declarative::Titlebar is typically overlaid on top of the contents (see example for a complete example with a blurred backdrop):

    setContents(Stacked {
    content,
    Vertical {
        Titlebar { Horizontal { Label { "My app" } } },
        SpacerExpanding {},
    },
});

    Window title inside the titlebar#

    You don't have to imitate the title of each OS yourself. Put declarative::WindowTitle into declarative::Titlebar (Titlebar {} without contents contains it) to mark where the title is, and the OS draws it there, the same way it does in its own titlebars, wherever it can:

    Who draws the title Where
    macOS AppKit (the native title) centered over the window horizontally, centered in declarative::Titlebar vertically
    Linux GTK/adw GTK (the native header bar title) like in a header bar: centered over the window while it fits into declarative::WindowTitle, otherwise shifted into it
    Windows AUI: DWM does not draw the caption text of windows with the extended client area left-aligned label
    Linux X11, Borderless windows AUI centered label

    The native title follows the system font, color and the inactive window look. It is drawn over the window contents, so neither ASS nor other views can affect it; it is shown only while declarative::WindowTitle is present (see AWindow::hasNativeWindowTitle). Where AUI draws the title, style it with t<AWindowTitle>().

    The result looks like an ordinary titlebar, but you control its background and can place your own views around the title:

    setContents(Stacked {
    content,
    Vertical {
        Titlebar {},   // looks like the OS titlebar
        SpacerExpanding {},
    },
});

    The window is the single source of truth for the title: AWindow::title is a property; the native title is the window title itself, and the AUI-drawn declarative::WindowTitle is bound to it. Change the title with AWindow::setTitle (or title() = ...), and the taskbar, window switcher and the title in your titlebar update together. Do not duplicate the title in a Label with a string literal. If you need a label of your own (for example, with a prefix), bind it to the property:

    Titlebar {
    Horizontal {
        Icon { ":img/logo.svg" },
        Label { .text = AUI_REACT("{} - Editor"_format(*window->title())) },
    },
}

    If you don't need contents in the titlebar area at all, use DecorationDefault: the OS draws the titlebar entirely.

    What Titlebar is and how its size is determined#

    declarative::Titlebar is not just a handle: it is a Horizontal { window controls (start), contents, window controls (end) } container which stretches horizontally over the whole width of its parent. Its size is not set by the window or the platform, it is regular AUI layout:

    • width: expanding, takes all the available width of the parent;
    • height: the maximum of the contents' height and the window controls' height (native controls height from AWindow::windowControlsInsets or AUI-drawn buttons height). To make the titlebar taller, put a taller view or padding into it. In a Borderless window it is just the height of the contents.

    The rectangle occupied by declarative::Titlebar after layout is what the window treats as the caption area: it is used for dragging and, on macOS and GTK, to vertically center the native window controls inside it.

    AWindow::windowControlsInsets is a property reporting the space occupied by native window controls (traffic lights on macOS, GtkWindowControls on GTK); AWindowControls uses it to keep the contents out of their way.

    Lifecycle#

    Only title and resizability can change at runtime:

    What API
    title AWindow::title property (AWindow::setTitle, titleChanged)
    resizability AWindow::setResizable / AWindow::isResizable
    visibility AWindow::show / AWindow::hide, reversible
    closing AWindow::close, terminal

    close() works the same on all platforms: closed is emitted exactly once, the modal parent is unblocked, the native window is destroyed. A closed window can't be shown again - create another one. Calling show() on a closed window logs an error and does nothing. Closing by the close button calls AWindow::onCloseButtonClicked, which calls close(); override it to refuse closing.

    Native handles#

    AWindow::nativeHandle returns the underlying native window object, which can be passed to platform APIs AUI does not wrap (DWM attributes, NSWindow tweaks, embedding into foreign toolkits, etc.). Its type is AWindowNativePtr and depends on the platform:

    Platform AWindowNativePtr What it points to
    Windows HWND the window itself
    macOS void* NSWindow* (AUIView is its content view)
    Linux, GTK4 / libadwaita backend std::uintptr_t GtkWindow*; GtkPopover* for popups
    Linux, X11 backend std::uintptr_t X11 Window (XID)
    Android, iOS, web jobject / void* not available: always null, the surface is owned by the activity, view controller or canvas

    The handle is null until the native window is created and after it is destroyed (see AWindow::close). It is owned by AUI: don't destroy it, don't keep it past AWindow::closed. Use it from the UI thread only.

    #include <AUI/Platform/AWindow.h>

void tweakNativeWindow(AWindow& window) {
#if AUI_PLATFORM_WIN
    HWND hwnd = window.nativeHandle();
    SetWindowTextW(hwnd, L"Hello from Win32");
#elif AUI_PLATFORM_APPLE
    // in an Objective-C++ (.mm) file:
    NSWindow* nsWindow = static_cast<NSWindow*>(window.nativeHandle());
    nsWindow.level = NSFloatingWindowLevel;
#elif AUI_PLATFORM_LINUX
    // see below
#endif
}

    Linux#

    Linux has two core platform APIs, chosen at runtime (see APlatformAbstractionOptions); on the application side there is no compile-time way to tell which one is active, so the same uintptr_t means a different thing depending on the backend. Decide which one you have yourself, i.e., by pinning APlatformAbstractionOptions::initializationOrder to a single backend before creating windows:

    // X11 only
APlatformAbstractionOptions::set({ .initializationOrder = { APlatformAbstractionOptions::X11{} } });
...
Window xid = static_cast<Window>(window.nativeHandle());
Display* display = XOpenDisplay(nullptr); // XIDs are valid on any connection to the same X server

    // GTK4 / libadwaita only
APlatformAbstractionOptions::set({ .initializationOrder = { APlatformAbstractionOptions::Gtk4{} } });
...
auto* gtkWindow = reinterpret_cast<GtkWindow*>(window.nativeHandle());

    AUI loads GTK dynamically, so it does not require GTK headers to build your application; include them yourself if you use the handle. To reach lower-level objects, go through GTK:

    • GdkSurface*: gtk_native_get_surface(GTK_NATIVE(gtkWindow))
    • Wayland wl_surface*: gdk_wayland_surface_get_wl_surface(gdkSurface) (when GDK_IS_WAYLAND_SURFACE)
    • X11 Window under GTK (i.e., GTK running on X11 or Xwayland): gdk_x11_surface_get_xid(gdkSurface) (when GDK_IS_X11_SURFACE)

    On a Wayland session without pinning the backend you will get the GTK flavor; the X11 backend works through Xwayland there and its handle is an XID.

    Platform specifics#

    Windows macOS Linux GTK/adw Linux X11 Android, iOS, web
    Default buttons window style bits; disabled close is greyed style mask decoration-layout of the header bar Motif hints (window manager may ignore) ignored
    Extended window controls drawn by AUI, hit-tested natively (snap layouts) native traffic lights, aligned to declarative::Titlebar native GtkWindowControls drawn by AUI none
    Extended title (declarative::WindowTitle) drawn by AUI native, aligned to declarative::Titlebar vertically native header bar title drawn by AUI drawn by AUI
    Borderless shadow DWM frame system shadow CSD shadow not available, shadow is ignored ignored
    parent owner window child window transient transient ignored
    modal parent is disabled parent ignores input gtk_window_set_modal _NET_WM_STATE_MODAL, parent ignores input ignored

    Known gaps (not related to decorations): minimize/maximize are stubs on macOS, there is no minimized signal on all platforms, moveToCenter is empty on Linux X11.

    Init#

    struct AWindow::Init

    Window creation parameters. Pass it to the AWindow constructor to open a window with a parent, modality, custom decorations or fixed size; for a plain window AWindow(title, width, height) is enough. See AWindow for how to open a window.

    Everything here except title and resizable is applied at window creation and can't be changed afterwards. title and resizable are the initial values; use AWindow::setTitle and AWindow::setResizable to change them at runtime.

    _new<AWindow>(AWindow::Init {
    .title = "Settings",
    .width = 400_dp,
    .height = 300_dp,
    .parent = AWindow::Init::Parent { .window = *this, .modal = true },
    .decoration = AWindow::Init::DecorationDefault { .buttons = { .minimize = false, .maximize = false } },
    .resizable = false,
});

    safeAreaInsets#

    AProperty<ABoxFields> safeAreaInsets

    Parts of the window covered by the system UI, in pixels.

    Padding that guarantees the useful content is not overlapped by anything the application does not control: the status bar, display cutout and navigation bar on Android and iOS; the window controls strip of AWindow::Init::DecorationExtended on desktop. Put it into padding of the root view:

    connect(window->safeAreaInsets, root, [root = root.get()](const ABoxFields& i) {
    root->setPadding(i);
});

    The system UI itself is not part of the content area, so on desktop the value is zero if the window decoration is the OS' one (AWindow::Init::DecorationDefault) or there is none (AWindow::Init::DecorationBorderless): the OS (or you) already positions the content below the titlebar.

    For AWindow::Init::DecorationExtended, top is the height of AWindow::windowControlsInsets; declarative::Titlebar lives inside that strip. Use AWindow::windowControlsInsets when you need to know which corners of the strip are occupied, since the controls take a corner of it, not the whole strip.

    The software keyboard is not a part of the safe area.

    close#

    void AWindow::close()

    Closes the window.

    Closing is terminal and works the same on all platforms: closed is emitted exactly once, the modal parent is unblocked, the native window is destroyed and the window is removed from the AWindowManager. The window can't be shown again after that; create another one. Calling close() on a closed window does nothing.

    Use AWindow::hide to hide the window temporarily.

    Examples:

    getMinimumSize#

    glm::ivec2 AWindow::getMinimumSize()

    The smallest size this window can be resized to.

    In contrast to AView::getMinSize, which is the explicitly styled minimum, this one is measured from the window's contents: a window is never smaller than the space its contents need at their narrowest, so its layout is never squeezed into nothing. The styled minimum is respected as well.

    The minimum height depends on the current width of the window (wrapped text needs less height in a wider window). Note that this differs from GTK and Qt, which use the height needed at the minimum width (a static value, the tallest the contents can be). As the minimum height changes along with the width, it is re-announced to the window manager on every layout; on win32 it may lag one resize step behind.
